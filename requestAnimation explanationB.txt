Historical working notes: requestAnimationFrame

Use the full tutorial in article/tutorial.md and the repository README as the
canonical explanations. This file preserves the original teaching-history
artifact and the decisions that shaped the finished example.

The browser gives each animation-frame callback a timestamp. Use that timestamp
to derive elapsed time instead of counting frames, because refresh rates and
frame delivery vary.

Carry these decisions into the example:

- Derive progress from the callback timestamp instead of assuming a frame rate.
- Treat requestAnimationFrame as a one-shot request whose callback schedules
  the next frame.
- Read the latest callback through a React Effect Event without reconnecting
  the scheduling effect.
- Cancel the latest request during pause, effect restart, and unmount cleanup.
- Prevent a callback from scheduling another request after synchronous
  teardown.
- Start a resumed timing sequence with a zero delta.
- Clamp negative deltas to zero and cap one long delta at 100 milliseconds.
- Stop JavaScript scheduling when prefers-reduced-motion requests less motion.
- Prefer CSS or the Web Animations API when JavaScript does not need to
  calculate each visual state.

When CSS can describe the motion, prefer CSS. Use requestAnimationFrame when
each frame depends on JavaScript state or browser timing.
